## 5. 代码审查发现

### P0 阻塞问题

#### P0-1: IMA 同步 ADMIN 越权(可同步他人素材卡到自己的 IMA)

- **文件:** `src/app/api/sync/route.ts:34`(单卡)、`:93`(批量)
- **风险:** ADMIN 角色在 owner 校验中被例外放行,可把**其他用户**的私有素材卡同步到**自己的** IMA 知识库。违反需求 2.3 / 5.2「ADMIN 只能把自己的素材卡同步到自己的 IMA」。
- **证据:**
```typescript
// route.ts:34 — 单卡
if (card.ownerUserId && card.ownerUserId !== user.id && user.role !== "ADMIN") {
  return forbiddenResponse("无权同步此素材卡");
}
// route.ts:93 — 批量
if (user.role !== "ADMIN") {  // ADMIN 直接跳过 owner 校验
  const unauthorized = existingCards.filter(c => c.ownerUserId && c.ownerUserId !== user.id);
  ...
}
```
- **修复建议:** 删除 ADMIN 例外,ADMIN 同步也必须 `card.ownerUserId === user.id`(ADMIN 如需运维代操作,应另开显式 admin-only 接口,默认拒绝):
```typescript
// 单卡
if (card.ownerUserId !== user.id) {
  return forbiddenResponse("只能同步自己的素材卡");
}
// 批量:过滤掉非自己的卡并报错
const unauthorized = existingCards.filter(c => c.ownerUserId !== user.id);
if (unauthorized.length > 0) return forbiddenResponse("只能同步自己的素材卡");
```

#### P0-2: SyncRecord 查询完全无 owner 隔离(数据泄露)

- **文件:** `src/services/ima-sync.ts:830-856` + `src/app/api/sync/route.ts:155-167`
- **风险:** `GET /api/sync?syncRecordId=X` 和 `GET /api/sync?cardId=Y` 调用 `getSyncStatus` / `getSyncHistory`,**这两个 service 函数完全不接收 userId、不过滤任何 owner 条件**。任何登录的 VERIFIED_USER 传任意 syncRecordId / cardId 都能读到**别人的同步记录和别人卡的同步历史**。这是确凿的数据泄露,违反需求 2.2「不可读取其他用户 SyncRecord」。
- **证据:**
```typescript
// ima-sync.ts:830 — getSyncStatus 无任何 userId 参数/过滤
export async function getSyncStatus(syncRecordId: string) {
  const record = await db.syncRecord.findUnique({
    where: { id: syncRecordId },  // 仅按 id 查,无 userId 条件
    include: { materialCard: { select: { id: true, title: true } } },
  });
  ...
}
// ima-sync.ts:847 — getSyncHistory 同样无 userId
export async function getSyncHistory(cardId: string, limit = 20) {
  return db.syncRecord.findMany({ where: { materialCardId: cardId }, ... });  // 仅按 cardId
}
// route.ts:155 — route 层也没传 user
const record = await getSyncStatus(syncRecordId);
```
- **修复建议:** service 函数加 userId 参数,route 层传入并校验:
```typescript
export async function getSyncStatus(syncRecordId: string, userId: string, isAdmin: boolean) {
  const record = await db.syncRecord.findUnique({ where: { id: syncRecordId }, include: {...} });
  if (!record) throw new NotFoundError();
  if (!isAdmin && record.userId !== userId) throw new NotFoundError(); // 非 owner 返回 404(隐藏存在)
  return record;
}
export async function getSyncHistory(cardId: string, userId: string, isAdmin: boolean, limit = 20) {
  // 先验卡归属
  const card = await db.materialCard.findUnique({ where: { id: cardId }, select: { ownerUserId: true } });
  if (!card || (!isAdmin && card.ownerUserId !== userId)) return []; // 非 owner 返回空
  return db.syncRecord.findMany({ where: { materialCardId: cardId, ...(isAdmin ? {} : { userId }) }, ... });
}
```
route 层:`getSyncStatus(syncRecordId, user.id, user.role === "ADMIN")`。

#### P0-3: IMA service 层无 owner 防线

- **文件:** `src/services/ima-sync.ts:390-420`(syncMaterialCard)、`:679-696`(syncArticle)
- **风险:** service 层只校验 `confirmed`,不校验 `ownerUserId`、不排除 `archivedAt != null`。一旦 route 层被绕过(或未来新增调用点),任何人能同步任意卡。违反需求 6.3「service 层也必须校验 owner」。syncArticle 还可能把**别人**的 confirmed 卡一起同步。
- **证据:**
```typescript
// ima-sync.ts:413 — 只校验 confirmed
if (!card.confirmed) { return { ... "MATERIAL_CARD_UNCONFIRMED" ... }; }
// 无 ownerUserId 校验,无 archivedAt 排除
// ima-sync.ts:679 — syncArticle 查 materialCards 只过滤 confirmed
materialCards: { where: { confirmed: true }, ... }  // 缺 ownerUserId: userId
```
- **修复建议:** service 层补独立防线:
```typescript
// syncMaterialCard:加 owner + archived 校验
if (userId && card.ownerUserId !== userId) return { ... "MATERIAL_CARD_FORBIDDEN" ... };
if (card.archivedAt) return { ... "MATERIAL_CARD_ARCHIVED" ... };
// syncArticle:materialCards where 加 ownerUserId: userId
materialCards: { where: { confirmed: true, ownerUserId: userId, archivedAt: null }, ... }
```

### P1 重要问题

#### P1-1: reject / downlist 状态合并,缺独立 downlist

- **文件:** `prisma/schema.prisma:190`
- **风险:** 只有 `adminReviewStatus`(pending_ai/pending_admin/approved/rejected),无 downlist。违反需求第 6 节「保留两个状态」。reject(审核拒绝)与 downlist(上线后下架)语义不同,影响恢复逻辑、审计、统计。
- **修复建议:** 枚举新增 `downlist`;migration 用 `publicVisibleAt` 启发式迁移历史数据(曾上线→downlist,从未上线→rejected);各处过滤(generate-card/review/sync/articles)适配两状态。详见修复阶段。

#### P1-2: ArticleReviewState 模型缺失

- **文件:** `prisma/schema.prisma`(全文无此 model)
- **风险:** 无法记录收藏文章的复习状态(mastery/reviewCount/nextReviewAt)。违反需求第 7 节。
- **修复建议:** 按需求第 7 节 schema 新增 model + migration + 复习 API。详见修复阶段。

#### P1-3: 前端收藏/已读/忽略按钮调用错误接口(死代码,按钮失效)

- **文件:** `src/app/articles/[id]/page.tsx:585-600`(toggleReadingState)、`src/app/api/content-items/[id]/route.ts:89`
- **风险(修正):** 复核 PUT 接口发现 `content-items/[id]` PUT 用的是 **`requireAdmin`**(:89),**普通用户调用直接返回 403**。因此前端 `toggleReadingState` 对 USER/VERIFIED_USER 是**死代码**——点击收藏/已读/忽略按钮实际 PUT 失败(403),用户状态写不进去,**按钮失效**。这不是数据污染(全局字段被 ADMIN-only 保护着),而是**功能 bug**:用户的学习状态操作静默失败。
- **证据:**
```typescript
// content-items route.ts:89 — PUT 是 ADMIN-only
const user = await requireAdmin(request);  // 非 ADMIN → 403
// page.tsx:591 — 前端却用普通用户身份 PUT 全局字段
body: JSON.stringify({ [field]: newValue }),  // field ∈ bookmarked|read|ignored → 403
```
- **修复建议:** 前端 `toggleReadingState` 改调正确接口:`read`/`ignored` → `PUT /api/user-content-state`;`bookmarked` → `/api/favorites`。`content-items/[id]` PUT 的 bookmarked/read/ignored 三个全局字段分支(:125-127)应移除(ADMIN 也不该用全局字段记用户状态)。详见修复阶段。

#### P1-4: /api/articles 允许匿名访问

- **文件:** `src/app/api/articles/route.ts:140-151`
- **风险:** 匿名返回 approved+public 文章,不返回 401。需求第 3 节明确「/api/articles 必须登录」。无数据泄露(只返回公共文章),但违反访问策略。
- **修复建议:** GET 入口改为 `requireAuth`,匿名返回 401。

### P2 建议

## 8. Playwright 结果

### 8.1 全量首轮(任务 bxsm3gd55,5 projects × ~580 用例)

首轮跑到 622 个用例结果(因 admin fixture 污染,主动停止,详见 §9):
- **passed:** 345 · **failed:** 223 · **skipped:** 57

### 8.2 ⚠️ 关键发现:首轮失败被「失效的 admin fixture」大面积污染

经逐项排查,首轮 223 个失败中**绝大多数由 `.auth/admin-storage.json` token 失效导致**,非真实代码回归:

- 直接验证:`curl -b <stored admin cookie> /api/admin/metrics` → **401「未登录或会话已过期」**
- 同一时刻 `curl -b <fresh admin cookie>` → **200**(fresh 登录正常)
- `verified-storage.json` / `usera-storage.json` cookie → 均 **200**(正常)
- `[userA]` project 失败用例**全部集中在 admin-* spec**(30 个),**非 admin spec 失败 0 个**——因 admin spec 用 `test.use({ storageState: '.auth/admin-storage.json' })` 覆盖身份,而该 fixture 失效

**根因:** global-setup 在 00:46 捕获 admin token,但全量 5-project 跑到 admin-gated spec 时已过 ~45 分钟,期间该 token 被失效(疑似 dev server hot-reload 重启轮换了会话/签名密钥,或某 admin spec 遥测/登出副作用)。stored cookie `expires:-1`(session cookie)而 fresh 登录返回 `Max-Age=86400`,佐证 token 状态不一致。

**结论:** 首轮 admin-gated spec 的失败**不可信**,需用有效 fixture 重跑。userA/userB/verified/anonymous 的非 admin 用例结果可信。

### 8.3 可信的真实失败(非 admin fixture 污染)
