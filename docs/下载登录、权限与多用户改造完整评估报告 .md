# shenlun-material-hub 登录、权限与多用户改造完整评估报告

> 报告用途：供项目负责人确认改造方向，并指导后续 Coding Agent 分阶段实施  
> 依据材料：
>
> - `AUTH_RBAC_ASSESSMENT_HANDOFF.md`
> - `AUTH_RBAC_REQUIREMENTS_ASSESSMENT.md`
> - `AUTH_RBAC_CODE_READING_MANIFEST.md`
>
> 报告结论：**项目适合进行登录、权限和多用户改造，但必须分阶段实施；当前第一优先级不是邀请码或个人配置，而是立即完成 API 安全收口与认证基础建设。**

## 一、执行摘要

### 1.1 当前项目处于什么状态

`shenlun-material-hub` 当前本质上仍是一个：

```text
单管理员账号
+ 全局公开数据
+ 全局配置
+ 大量公开 API
```

的单用户内容管理工具。

项目已经具备较完整的业务能力，包括：

- 文章浏览；
- 网站采集；
- WeWe RSS 同步；
- AI 评估；
- 素材卡生成；
- IMA 同步；
- 任务管理；
- 管理后台；
- 数据备份；
- 数据清洗；
- 系统日志。

但当前登录能力只保护了管理后台页面入口，并没有真正形成服务端权限体系。大量高风险接口仍可以在未登录状态下直接调用。

### 1.2 当前最严重的问题

最严重的问题不是“还没有普通用户登录页”，而是：

1. 数据库中没有用户表、会话表和角色模型；
2. 当前只有环境变量中的单一管理员；
3. 约 31/35 个 API 没有认证保护；
4. 管理 API、备份、清洗、AI 调用、采集和同步接口存在未授权访问风险；
5. 所有文章、素材卡、任务和同步记录没有用户归属；
6. AI、IMA、WeWe RSS 主要使用全局配置；
7. 异步任务没有用户上下文，无法安全支持多用户；
8. 当前密码哈希方式不适合作为正式多用户密码系统。

### 1.3 是否适合继续开发

**适合。**

当前技术栈为 Next.js App Router、Prisma、PostgreSQL、React、Tailwind、Vitest 和 Playwright，能够支持多用户权限改造。

但不能一次性同时开发：

- 登录；
- 邀请码；
- 多角色；
- 数据隔离；
- 用户级 AI；
- 用户级 WeWe RSS；
- 多 IMA；
- 管理员查看用户密钥；
- 任务限额。

如果一次性全部修改，极易破坏现有采集、AI、同步和公开浏览能力。

### 1.4 推荐总体路线

推荐按以下四个阶段实施：

| 阶段 | 目标 | 核心结果 |
|---|---|---|
| 第一阶段 | 安全收口与认证基础 | 建立用户、会话、角色；保护全部危险 API |
| 第二阶段 | 多用户数据隔离 | 文章、素材卡、任务、同步记录按用户隔离 |
| 第三阶段 | 用户个人配置与认证用户能力 | 用户自己的 AI、WeWe RSS、IMA；开放认证用户采集 |
| 第四阶段 | 高级能力 | 邀请码、多 IMA、任务限额、完整审计和高风险密钥查看评估 |

## 二、当前项目架构

### 2.1 技术栈

| 层级 | 当前技术 |
|---|---|
| 全栈框架 | Next.js 16 App Router |
| 前端 | React 19、Tailwind CSS 4、shadcn/ui |
| 后端 | Next.js Route Handlers |
| ORM | Prisma 7 |
| 数据库 | PostgreSQL (pg) |
| AI | OpenAI SDK |
| 测试 | Vitest、Playwright |
| 部署 | Docker，Next.js standalone |
| 包管理 | pnpm |

### 2.2 当前数据模型

当前数据库约有 11 张核心表：

- `Source`
- `CollectionChannel`
- `ContentItem`
- `MaterialCard`
- `SyncRecord`
- `CollectorRun`
- `AiConfig`
- `AiPromptTemplate`
- `ArticleAnnotation`
- `SystemLog`
- `AsyncTask`

当前不存在：

- `User`
- `Session`
- `Invitation`
- `InvitationUse`
- `UserIntegration`
- `ImaTarget`
- `UserContentRelation`
- 专门的安全审计日志模型

当前所有业务数据均没有明确的用户归属字段。

### 2.3 当前认证方式

当前认证为单管理员模式：

- 管理员用户名来自环境变量；
- 管理员密码哈希来自环境变量；
- 使用自定义 JWT；
- Cookie 保存认证状态；
- JWT 仅表达“是否已认证”；
- 没有角色；
- 没有数据库 Session；
- 没有会话撤销能力；
- 用户被禁用、角色变化或密码重置后，无法立即让旧 Token 失效。

### 2.4 当前配置方式

| 配置 | 当前方式 | 当前范围 |
|---|---|---|
| AI API Key / Base URL / Model | 数据库 `AiConfig` + 环境变量 fallback | 全局 |
| IMA 配置 | 环境变量 | 全局 |
| WeWe RSS | 环境变量或请求参数 | 全局 |
| AI 提示词 | 数据库 | 全局 |
| 管理员账号 | 环境变量 | 单一管理员 |

### 2.5 当前任务系统

当前任务系统为进程内队列：

- 任务信息写入 `AsyncTask`；
- 队列运行在应用进程内；
- 默认全局并发为 2；
- 没有用户归属；
- 没有用户级并发；
- 没有完善重试机制；
- 任务执行时无法确定应该使用哪个用户的配置。

## 三、当前安全问题

### 3.1 API 权限问题

评估报告显示，约 35 个 API 中只有极少数认证相关接口具备认证逻辑，绝大部分接口没有认证保护。

高风险接口包括：

- 管理任务；
- 系统日志查看和删除；
- 系统指标；
- 数据备份导出；
- 数据备份导入；
- 数据清洗；
- AI 配置修改；
- AI 提示词修改；
- 网站采集；
- 微信/WeWe RSS 同步；
- AI 评估；
- 素材卡生成；
- IMA 同步；
- 来源增删改；
- 导出；
- 批注写入；
- 复习状态修改。

这意味着，仅保护 `/admin` 页面是不够的。攻击者可以绕过页面，直接请求 API。

### 3.2 水平越权风险

当前按 ID 操作的接口没有用户归属验证，例如：

- 查看任意文章；
- 修改任意文章；
- 删除任意文章；
- 为任意文章生成素材卡；
- 同步任意素材卡；
- 修改任意批注；
- 删除任意批注。

在多用户系统中，如果不系统性改造这些接口，用户 A 可以通过修改 URL 或请求参数访问用户 B 的数据。

### 3.3 垂直越权风险

当前没有角色系统。

如果未来只简单增加普通用户登录，但继续沿用“已登录即管理员”的判断方式，普通用户可能直接获得管理员能力。

### 3.4 配置泄露风险

当前风险包括：

- AI 配置接口未充分保护；
- 备份接口可能导出包含密文配置的完整数据库；
- 管理接口可能暴露服务器内部信息；
- 用户级配置尚不存在，后续若使用全局缓存，容易发生串用户；
- 当前加密方案虽可用，但密钥派生方式和主密钥管理仍需要加强。

### 3.5 任务串用户风险

当前 `AsyncTask` 没有 `userId`。

若直接开放认证用户采集或 AI 操作，会出现：

- 任务无法确认是谁创建的；
- 任务可能使用错误用户的 AI Key；
- 同步任务可能写入错误用户的 IMA；
- 管理员无法区分任务归属；
- 用户可能看到或重试其他人的任务。

## 四、已确认的产品方向

### 4.1 计划中的身份模型

最终计划区分：

| 身份 | 角色 | 最终目标权限 |
|---|---|---|
| 访客 | 无角色 | 浏览公开内容 |
| 普通用户 | `USER` | 登录但只能浏览 |
| 认证用户 | `VERIFIED_USER` | 使用自己的配置采集、AI 处理和同步 |
| 管理员 | `ADMIN` | 管理用户、来源、公共内容和系统任务 |

保留 `USER` 与 `VERIFIED_USER` 是合理的。

原因是：

- 普通注册账号不应自动获得采集和 AI 消耗能力；
- 管理员可以控制哪些用户能调用外部服务；
- 可以避免未经认证用户滥用服务器和付费 API。

### 4.2 注册方式

最终计划使用邀请码注册。

但邀请码不应在第一阶段开发，因为第一阶段的核心任务是安全收口和认证基础。邀请码涉及：

- 新数据表；
- 并发扣减；
- 使用次数；
- 有效期；
- 防枚举；
- 注册流程；
- 管理页面。

建议在认证基础稳定后再开发。

### 4.3 历史文章

已确认历史文章默认保持公开。

这一选择合理，因为当前文章本来就是全局公开浏览。若升级后突然全部私有，会破坏现有使用体验。

建议：

- 历史文章：`public`
- 认证用户新采集文章：默认 `private`
- 历史素材卡：需要在第二阶段迁移前进一步确认归属
- 用户未来生成的素材卡：默认 `private`

### 4.4 多 IMA

已确认最终每个认证用户支持多个 IMA 知识库。

但当前 IMA 配置完全依赖环境变量，服务文件在模块加载时读取全局配置，因此多 IMA 属于较大重构，应放到第三或第四阶段。

### 4.5 管理员查看用户明文密钥

产品方向允许管理员查看，但代码评估明确指出该能力安全风险较高。

建议当前处理方式：

- 第一至第三阶段不开发；
- 先完成用户级配置、审计日志和管理员二次验证；
- 后续单独进行安全设计评估；
- 默认仍只显示掩码；
- 不允许批量查看或导出；
- 必须记录查看原因与审计记录。

## 五、评估报告中需要纠正或补充的地方

### 5.1 Git 根目录描述存在矛盾

交接报告称项目不在 Git 管理下，但代码阅读清单又指出：

- 外层目录无 `.git`
- 内层真实项目目录存在 `.git`

后续 Agent 必须进入真正包含以下内容的目录操作：

```text
.git/
package.json
src/
prisma/
```

否则可能在错误目录创建分支或修改文件。

### 5.2 评估阶段没有运行测试

评估阶段未运行 lint、test、build 和 Playwright。

这不影响架构判断，但意味着：

- 当前项目是否已经存在测试失败，尚未确认；
- 后续开发前必须先建立测试基线；
- 不能把开发后出现的所有失败都认定为新改动导致。

### 5.3 阅读覆盖并非全部逐行阅读

代码阅读清单显示：

- 已完整阅读约 68 个文件；
- 仅确认用途约 42 个；
- 未阅读约 50 个。

核心认证、API、配置和任务模块覆盖较好，因此总体结论可信。

但正式开发前，Agent 仍应补充阅读：

- 所有未完整阅读的写入接口；
- 所有素材卡 CRUD；
- 所有来源 CRUD；
- 所有 WeWe RSS 管理接口；
- 所有现有 API 测试；
- 现有 Playwright 测试。

### 5.4 不建议认证用户自动回退管理员配置

评估报告曾建议用户没有 AI 配置时回退到系统配置。

这不符合最终产品方向。

后续应采用：

- 管理员可使用系统配置；
- 认证用户必须使用自己的配置；
- 用户未配置时显示明确提示；
- 不自动消耗管理员的 AI Key 或同步到管理员的 IMA。

## 六、推荐的阶段实施方案

# 第一阶段：安全收口与认证基础

## 6.1 阶段目标

第一阶段只解决：

- 谁能登录；
- 谁是什么角色；
- 谁可以调用什么 API；
- 如何立即撤销用户会话；
- 如何保护当前高风险接口。

第一阶段不解决用户数据归属和个人配置。

## 6.2 第一阶段身份权限

| 身份 | 第一阶段实际权限 |
|---|---|
| 访客 | 浏览公开页面 |
| USER | 登录、浏览、修改自己密码、退出 |
| VERIFIED_USER | 第一阶段暂时与 USER 一样只读 |
| ADMIN | 使用现有全部管理和写入功能 |

之所以第一阶段暂时不向 `VERIFIED_USER` 开放采集，是因为：

- 数据尚未按用户隔离；
- 任务没有用户上下文；
- 用户个人 AI/IMA/WeWe RSS 尚未完成；
- 开放后会继续写入全局数据并使用全局配置。

## 6.3 第一阶段必须完成

### 数据库

新增：

- `User`
- `Session`
- 角色字段；
- 用户状态；
- 会话失效机制。

### 认证

实现：

- 通用 `/login`；
- 数据库 Session；
- 高熵随机 Session Token；
- 数据库只保存 Token 哈希；
- 用户禁用后立即失效；
- 密码重置后立即失效；
- 角色变化后立即失效；
- 退出登录；
- 当前用户接口。

### 密码

- 停止为新账号使用普通 SHA-256；
- 优先使用 Argon2id；
- 若原生依赖影响部署，则使用 bcrypt；
- 首个管理员通过幂等初始化脚本迁移。

### API 安全收口

保持公开：

- 公开文章列表；
- 公开文章详情；
- 公开搜索；
- 公开探索和推荐所需接口。

暂时仅允许管理员：

- 采集；
- WeWe RSS 同步；
- AI 评估；
- 素材卡生成；
- IMA 同步；
- 来源修改；
- AI 配置；
- 提示词配置；
- 数据备份；
- 数据清洗；
- 日志管理；
- 系统指标；
- 管理后台；
- 所有写入和破坏性操作。

### 前端

实现：

- 通用登录页；
- 用户菜单；
- 角色状态；
- 管理员入口；
- 按角色隐藏按钮；
- 登录状态加载时避免越权按钮闪现；
- 管理员用户管理页面。

### 管理员用户管理

支持：

- 创建用户；
- 创建 USER 或 VERIFIED_USER；
- 修改角色；
- 启用/禁用；
- 重置密码；
- 撤销全部会话；
- 禁止禁用或降级最后一个管理员。

## 6.4 第一阶段验收标准

必须确认：

- 未登录用户无法调用任何危险写入 API；
- USER 无法调用写入和管理 API；
- VERIFIED_USER 第一阶段仍无法调用写入和管理 API；
- ADMIN 可以继续使用现有功能；
- 公开文章浏览正常；
- 备份、清洗、日志删除等高风险接口已保护；
- 用户被禁用、重置密码、修改角色后旧会话立即失效；
- lint、test、build、Playwright 全部完成并记录结果。

# 第二阶段：多用户数据隔离

## 6.5 阶段目标

第二阶段解决：

- 哪些内容属于哪个用户；
- 哪些内容公开；
- 哪些内容私有；
- 用户能查看和修改哪些数据；
- 异步任务属于谁。

## 6.6 推荐数据设计

推荐采用：

```text
共享文章主体
+ 用户文章关系表
+ 用户独立素材卡
```

### 共享文章主体

`ContentItem` 继续保留 `originalUrl` 唯一约束。

好处：

- 同一篇文章不会重复存储；
- 保留当前去重逻辑；
- 多用户可以关联同一篇文章；
- 减少采集与存储浪费。

### 用户关系表

建议新增类似：

```text
UserContentRelation
```

记录：

- 用户；
- 文章；
- 是否由该用户采集；
- 是否收藏；
- 是否进入复习；
- 用户自己的状态；
- 私有/公开关联信息。

### 素材卡

`MaterialCard` 建议增加：

- `ownerUserId`
- 可见性；
- 创建者；
- 用户独立编辑结果。

不同用户可以基于同一文章生成不同素材卡。

## 6.7 第二阶段改造范围

- ContentItem 可见性；
- 用户文章关系；
- MaterialCard 用户归属；
- ArticleAnnotation 用户归属；
- Review 用户归属；
- AsyncTask 用户归属；
- SyncRecord 用户归属；
- 列表过滤；
- 详情权限；
- 搜索过滤；
- 导出过滤；
- 统计过滤；
- 批量操作权限；
- 水平越权测试；
- 历史数据迁移。

# 第三阶段：用户个人配置与认证用户能力

## 6.8 阶段目标

完成认证用户真正可用的个人工作能力：

- 用户自己的 AI；
- 用户自己的 WeWe RSS；
- 用户自己的 IMA；
- 后台任务使用正确用户配置；
- 向 VERIFIED_USER 开放采集和 AI 能力。

## 6.9 AI 用户级配置

当前 AI 配置是全局配置。

改造后应：

- 每个认证用户拥有自己的 AI 配置；
- AI Key 加密存储；
- 只显示掩码；
- 用户未配置时明确提示；
- 不自动回退管理员配置；
- AI Runtime 缓存按用户隔离；
- 异步任务保存用户上下文；
- 所有 AI 调用必须显式使用正确用户配置。

## 6.10 WeWe RSS 用户级配置

WeWe RSS 服务层已经大量参数化，改造相对容易。

需要：

- 用户配置表；
- 用户自己的服务地址和凭证；
- 用户自己的同步记录；
- 用户自己的任务归属；
- 防止不同用户同步数据串联；
- 禁止多用户模式使用不安全的共享 SQLite 路径回退。

## 6.11 IMA 用户级配置

当前 IMA 是全局环境变量配置，改造较深。

需要：

- 将模块级环境变量改成函数配置参数；

## 十、最终结论

### 是否应该继续开发

**应该继续。**

### 是否应该一次性完成所有需求

**不应该。**

### 当前第一优先级

**立即保护全部危险 API，并建立可撤销的数据库用户会话和角色系统。**

### 当前不应开发的功能

- 邀请码；
- 用户级 AI；
- 用户级 WeWe RSS；
- 多 IMA；
- 管理员查看用户明文密钥；
- 向认证用户直接开放采集。

### 推荐最终路线

```text
安全收口与认证基础
→ 多用户数据隔离
→ 用户个人配置与认证用户采集能力
→ 邀请码、多 IMA、任务限额和完整审计
```

按照该路线推进，可以最大限度避免：

- 现有公开文章突然不可用；
- 采集和 AI 功能被破坏；
- 用户数据串联；
- 用户错误使用管理员密钥；
- 未授权访问管理和破坏性 API；
- 一次性大改造导致项目难以回滚。
